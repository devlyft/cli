# Releasing

Releases are automated. Nobody tags by hand.

## How a release happens

1. Pull requests are squash-merged into `main` with a [Conventional Commits](https://www.conventionalcommits.org/) title (enforced by the `Lint title` check).
2. On every push to `main`, [release-please](https://github.com/googleapis/release-please) updates an open release PR with the next version and the changelog, worked out from those titles.
3. Merging the release PR creates the GitHub release and the `vX.Y.Z` tag.
4. The tag triggers `.github/workflows/release.yml`, which runs [goreleaser](https://goreleaser.com/) on a GitHub-hosted runner to:
   - build `devlyft` for Linux, macOS and Windows on amd64 and arm64 (`CGO_ENABLED=0`, `-trimpath`, version, commit and date stamped in);
   - package `.tar.gz` archives (`.zip` on Windows) with an SPDX SBOM per archive, generated by syft;
   - write `devlyft_<version>_checksums.txt` covering every archive and SBOM;
   - sign the checksum file with [cosign](https://docs.sigstore.dev/) keyless signing, using the workflow's GitHub OIDC identity (no stored keys), producing `.sig`, `.pem` and `.sigstore.json`;
   - attach everything to the release.
5. The workflow then records a GitHub build-provenance attestation for the archives and the checksum file.

Every pull request also runs `checks / release-snapshot`, which builds all targets with the same config but skips signing, SBOMs and publishing. Run the same thing locally with `make snapshot`; the output lands in `dist/`.

## Verifying a download

Download the archive, `devlyft_<version>_checksums.txt` and `devlyft_<version>_checksums.txt.sigstore.json` from the release, then:

```sh
cosign verify-blob \
  --bundle devlyft_<version>_checksums.txt.sigstore.json \
  --certificate-identity-regexp '^https://github\.com/devlyft/cli/\.github/workflows/release\.yml@refs/tags/v' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  devlyft_<version>_checksums.txt

sha256sum --ignore-missing -c devlyft_<version>_checksums.txt
```

With the GitHub CLI you can check the build provenance instead:

```sh
gh attestation verify devlyft_<version>_linux_amd64.tar.gz --repo devlyft/cli
```

## Versioning: 0.x and 1.0

The CLI follows [semantic versioning](https://semver.org/).

- **While 0.x**, a minor release may contain breaking changes (`feat!:` and `BREAKING CHANGE` bump the minor, not the major). Patch releases never break.
- **1.0** is cut once all of these are true:
  - browser login (OAuth 2.0 with PKCE) is released ([devlyft/devlyft#263](https://github.com/devlyft/devlyft/issues/263));
  - device login is released ([devlyft/devlyft#264](https://github.com/devlyft/devlyft/issues/264));
  - the output-stability and deprecation policy is published.
- 1.0 is **not** gated on server-side pagination or rollout status. Until those ship, `--limit` and `deploy --wait` are documented as best-effort.
- **From 1.0**, breaking the documented JSON or YAML output, exit codes or error `code` strings requires a major release.

To cut 1.0, merge a commit containing `Release-As: 1.0.0` in its body; release-please will propose 1.0.0 in its next release PR.

## Known gaps

- macOS binaries are not notarized and Windows binaries are not code-signed, so browser downloads trigger Gatekeeper and SmartScreen warnings. Installing through Homebrew or the install script avoids this.
- Homebrew, Scoop, deb and rpm channels are tracked separately (devlyft/devlyft#258, devlyft/devlyft#260).
