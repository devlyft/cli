# Releasing

Releases are automated. Nobody tags by hand.

## How a release happens

1. Pull requests are squash-merged into `main` with a [Conventional Commits](https://www.conventionalcommits.org/) title (enforced by the `Lint title` check).
2. On every push to `main`, [release-please](https://github.com/googleapis/release-please) updates an open release PR with the next version and the changelog, worked out from those titles.
3. Merging the release PR creates the GitHub release and the `vX.Y.Z` tag.
4. The tag triggers `.github/workflows/release.yml`, which runs [goreleaser](https://goreleaser.com/) on a GitHub-hosted runner to:
   - build `devlyft` for Linux, macOS and Windows on amd64 and arm64 (`CGO_ENABLED=0`, `-trimpath`, version, commit and date stamped in);
   - package `.tar.gz` archives (`.zip` on Windows) with an SPDX SBOM per archive, generated by syft;
   - build `.deb` and `.rpm` packages for Linux amd64 and arm64 with [nfpm](https://nfpm.goreleaser.com/) (binary in `/usr/bin`, licence and README in `/usr/share/doc/devlyft`);
   - write `devlyft_<version>_checksums.txt` covering every archive, package and SBOM;
   - sign the checksum file with [cosign](https://docs.sigstore.dev/) keyless signing, using the workflow's GitHub OIDC identity (no stored keys), producing `.sig`, `.pem` and `.sigstore.json`;
   - attach everything to the release;
   - push a Scoop manifest (`bucket/devlyft.json`) to [devlyft/scoop-bucket](https://github.com/devlyft/scoop-bucket) using the `SCOOP_BUCKET_GITHUB_TOKEN` secret. When that secret is not set, the manifest is built but not pushed and the release still succeeds.
5. goreleaser also generates a Homebrew cask and pushes it to [devlyft/homebrew-tap](https://github.com/devlyft/homebrew-tap) (`Casks/devlyft.rb`), so `brew install devlyft/tap/devlyft` picks up the release. The push uses the `HOMEBREW_TAP_GITHUB_TOKEN` secret; when that secret is not set, the cask is built but not pushed and the release still succeeds. The cask installs bash, zsh and fish completions by running `devlyft completion <shell>`, and on macOS clears the quarantine attribute because the binary is not notarized.
6. The workflow then records a GitHub build-provenance attestation for the archives, the Linux packages and the checksum file.

Every pull request also runs `checks / release-snapshot`, which builds all targets with the same config but skips signing, SBOMs and publishing, then runs `install.sh` against the snapshot (and checks it rejects a tampered archive), installs the `.deb` on the runner and the `.rpm` in a Fedora container, and checks the Scoop manifest. Run the same thing locally with `make snapshot`; the output lands in `dist/`.

### Setting up the Homebrew tap

One-off, before the first release that should reach Homebrew:

1. Create the public repository `devlyft/homebrew-tap` with a README and a `Casks/` directory. Homebrew maps `devlyft/tap` to `github.com/devlyft/homebrew-tap`.
2. Create a credential that can write only to that repository: a fine-grained personal access token owned by a bot account (or a GitHub App installation token) with **Contents: read and write** on `devlyft/homebrew-tap` and nothing else.
3. Store it as the `HOMEBREW_TAP_GITHUB_TOKEN` secret in `devlyft/cli`, ideally in a protected environment used only by the release workflow.

### Setting up the Scoop bucket

One-off, before the first release that should reach Scoop:

1. Create the public repository `devlyft/scoop-bucket` with a README and a `bucket/` directory.
2. Create a credential that can write only to that repository: a fine-grained personal access token owned by a bot account (or a GitHub App installation token) with **Contents: read and write** on `devlyft/scoop-bucket` and nothing else.
3. Store it as the `SCOOP_BUCKET_GITHUB_TOKEN` secret in `devlyft/cli`, ideally in a protected environment used only by the release workflow.

### Linux packages

The `.deb` and `.rpm` files are attached to each GitHub release. They are not GPG-signed and there is no apt or yum repository yet; verify them through the signed checksum file like any other download (see below), then `sudo dpkg -i` or `sudo rpm -i` them. Shell completions and man pages are not packaged yet; man pages come with devlyft/devlyft#248.

## The install script

`install.sh` (served from `main` via raw.githubusercontent.com) installs on Linux and macOS:

1. Works out the OS and architecture, and the version: `DEVLYFT_VERSION`, or the latest release.
2. Downloads the archive and `devlyft_<version>_checksums.txt`.
3. If cosign is installed, downloads `devlyft_<version>_checksums.txt.sigstore.json` and verifies it with the same identity and issuer as below; any failure, including a missing bundle, aborts. Without cosign it warns and continues, unless `DEVLYFT_REQUIRE_SIGNATURE=1`, in which case it aborts.
4. Checks the archive's sha256 against the checksum file and aborts on a mismatch.
5. Installs `devlyft` into `DEVLYFT_INSTALL_DIR`, `/usr/local/bin` if writable, or `~/.local/bin`. It never calls sudo.

`DEVLYFT_DOWNLOAD_BASE` points it at another directory of release assets (a mirror, or `file://$PWD/dist` for testing) and requires `DEVLYFT_VERSION`.

## Verifying a download

Download the archive, `devlyft_<version>_checksums.txt` and `devlyft_<version>_checksums.txt.sigstore.json` from the release, then:

```sh
cosign verify-blob \
  --bundle devlyft_<version>_checksums.txt.sigstore.json \
  --certificate-identity-regexp '^https://github\.com/devlyft/cli/\.github/workflows/release\.yml@refs/tags/v' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  devlyft_<version>_checksums.txt

sha256sum --ignore-missing -c devlyft_<version>_checksums.txt
```

With the GitHub CLI you can check the build provenance instead:

```sh
gh attestation verify devlyft_<version>_linux_amd64.tar.gz --repo devlyft/cli
```

## Versioning: 0.x and 1.0

The CLI follows [semantic versioning](https://semver.org/).

- **While 0.x**, a minor release may contain breaking changes (`feat!:` and `BREAKING CHANGE` bump the minor, not the major). Patch releases never break.
- **1.0** is cut once all of these are true:
  - browser login (OAuth 2.0 with PKCE) is released ([devlyft/devlyft#263](https://github.com/devlyft/devlyft/issues/263));
  - device login is released ([devlyft/devlyft#264](https://github.com/devlyft/devlyft/issues/264));
  - the output-stability and deprecation policy is published.
- 1.0 is **not** gated on server-side pagination or rollout status. Until those ship, `--limit` and `deploy --wait` are documented as best-effort.
- **From 1.0**, breaking the documented JSON or YAML output, exit codes or error `code` strings requires a major release.

To cut 1.0, merge a commit containing `Release-As: 1.0.0` in its body; release-please will propose 1.0.0 in its next release PR.

## Known gaps

- macOS binaries are not notarized and Windows binaries are not code-signed, so browser downloads trigger Gatekeeper and SmartScreen warnings. Installing through Homebrew or the install script avoids this.
- The install script supports Linux and macOS only; Windows users install with Scoop or the zip archive.
- The `.deb` and `.rpm` packages are not GPG-signed and are not served from an apt or yum repository.
