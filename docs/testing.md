# Testing

There is no local DevLyft stack, so the CLI is tested in four layers that need none, plus a smoke test against production. Everything except the smoke test runs on every pull request on Linux, macOS and Windows.

| Layer | What it proves | Where | Runs |
|---|---|---|---|
| Unit | Commands do the right thing with the API's answers | `*_test.go` next to the code, gomock client | `make test`, every PR |
| Contract | Every request the facade sends, and every canned response, matches the vendored OpenAPI specs | `internal/api/contract_test.go`, `internal/testutil/apitest` | every PR |
| CLI behaviour | What a user sees: stdout, stderr and exit codes | golden files and testscript scripts in `internal/cli/testdata` | every PR |
| Smoke | The real binary works against the real API | `test/smoke` (build tag `smoke`) | nightly, by hand, from a release |

`make check` runs lint, tests, the coverage floor and govulncheck, as CI does.

## Unit tests: gomock, never hand-rolled fakes

Commands depend on `api.Client`, never on HTTP. Tests use the generated mock in `internal/api/mock` (regenerated by `make generate`), so a change to the interface breaks the build instead of silently leaving a fake behind.

Commands get the client from `cmdutil.Factory.Client()`. `internal/testutil/clitest` runs the whole CLI in-process with a mock injected, buffered streams, and an optional terminal:

```go
func TestProjectsList(t *testing.T) {
	m := mock.NewMockClient(gomock.NewController(t))
	m.EXPECT().ListProjects(gomock.Any(), orgID).Return(projects, nil)

	res := clitest.Run(t, &clitest.Options{Args: []string{"projects", "list", "--org", orgID}, API: m})
	golden.Assert(t, "testdata/projects_list.golden", res.Transcript())
}
```

`clitest.Options` also takes `TTY` (stdin, stdout and stderr look like a terminal, so tables, colour and prompts behave as they would interactively), `Stdin` (answers to prompts), `Env` (set with `t.Setenv`, so the test cannot be parallel), `Context` (for example a cancelled one, to test Ctrl-C) and `Commands` (extra commands, for fixtures).

Tests of package `cli` that use `clitest` live in package `cli_test`, because `clitest` imports `cli`.

## Contract tests

`internal/testutil/apitest` starts an `httptest` server from the vendored specs in `internal/api/specs`. Each request must match an operation and its parameters and body; each canned 2xx response must match the documented schema. Anything else fails the test.

```go
srv := apitest.NewServer(t, map[string]apitest.Response{
	"GetV1Organizations": {Body: `{"organizations":[]}`},
	"GetV1DeploysDeployId": {Status: 404, Body: `{"error":"not found"}`},
})
c, _ := api.New(api.Options{BaseURL: srv.URL, HTTPClient: srv.Client()})
```

`TestContract` in `internal/api` calls every facade method and checks that every vendored operation is exercised, so the allowlist (`internal/api/specs/allowlist.yaml`) never carries an endpoint the CLI does not use. When a spec update changes a request or response shape the CLI relies on, this is the test that fails.

## CLI behaviour: golden files and scripts

**Golden files** (`internal/cli/testdata/*.golden`) pin the full output of an invocation: the command line, the exit code, stdout and stderr. They cover every output format, every error code and exit code, usage errors and confirmation prompts. After an intended change to output, regenerate and review:

```sh
go test ./internal/cli/ -run TestGolden -update
git diff internal/cli/testdata
```

The `-update` flag comes from `internal/testutil/golden` and works in any package that uses `golden.Assert`.

**Scripts** (`internal/cli/testdata/script/*.txtar`) run the compiled CLI as a separate process with [testscript](https://pkg.go.dev/github.com/rogpeppe/go-internal/testscript), so they see real exit codes, real stdout and stderr, and the environment. Besides the standard testscript commands they have:

- `exitcode N devlyft ...`: run and require exit code N; stdout and stderr can then be checked with `stdout` and `stderr`.
- `fakeapi`: serve the script's `api/` directory as a fake API and set `DEVLYFT_API_URL`. `GET /v1/projects` is answered with `api/GET/v1/projects.json`, anything else with 404. Unlike `apitest`, it does not validate against the specs; use it for end-to-end flows, and `apitest` for request shapes.

```
exitcode 2 devlyft nope
! stdout .
stderr '^Error: unknown command "nope" for "devlyft"$'
```

Run one script with `go test ./internal/cli/ -run TestScripts/version`.

## Coverage

CI fails if statement coverage of `internal/` falls below 80% (`make cover-check`). Coverage counts across packages, so code exercised through the CLI counts for the package it lives in. Generated clients, mocks and the test harness are excluded. `make cover` writes `coverage.out`; `go tool cover -html=coverage.out` shows what is missing.

## Smoke test against production

`test/smoke` builds the binary and talks to the production API as a dedicated test organization. It is behind the `smoke` build tag, so `go test ./...` never runs it, and its workflow (`.github/workflows/smoke.yml`) runs nightly, by hand, or when called from another workflow in this repository. It never runs for pull requests, so forks cannot reach its secrets.

What it checks:

- `TestBinary`: the CLI builds and `devlyft version` works.
- `TestRead`: the token is accepted and the test organization and its projects can be read.
- `TestDeployLifecycle`: creates a build and a throwaway deploy (`smoke-<unix time>`), reads it back, and deletes the deploy in cleanup. It changes production state, so it only runs with `DEVLYFT_SMOKE_WRITE=1` and is off in the workflow for now. The API has no build deletion, so each run leaves one build behind in the test project.

Run it locally:

```sh
DEVLYFT_API_TOKEN=<org API token> DEVLYFT_SMOKE_ORG=<org UUID> \
  go test -tags smoke -count=1 -v ./test/smoke/
```

Without those variables every test skips. `DEVLYFT_API_URL` points it elsewhere. The write test also needs `DEVLYFT_SMOKE_WRITE=1`, `DEVLYFT_SMOKE_PROJECT`, `DEVLYFT_SMOKE_ENV`, `DEVLYFT_SMOKE_LOCATION` and `DEVLYFT_SMOKE_IMAGE` (`repo:tag`).

### One-off setup

1. Create a dedicated organization for smoke tests, with one project and environment, and nothing else in it.
2. Create an organization API token for it, with the shortest expiry that is practical, and a calendar reminder to rotate it.
3. In `devlyft/cli` → Settings → Environments, create an environment named `smoke`:
   - Deployment branches and tags: selected branches, `main` only.
   - Required reviewers are optional; with them, nightly runs wait for approval.
4. Add two environment secrets to `smoke`: `DEVLYFT_SMOKE_API_TOKEN` (the token) and `DEVLYFT_SMOKE_ORG` (the organization's UUID).
5. Run the workflow once by hand (Actions → Smoke → Run workflow) to confirm.

To run the smoke test on every release, add a job to `release.yml` with `uses: ./.github/workflows/smoke.yml` and `secrets: inherit` after the release job.

## Vulnerability scanning

`make vuln` runs govulncheck over the code that ships. Like `_test.go` files, the test harness in `internal/testutil` is left out: it runs kin-openapi's request validator over our own fixtures, and kin-openapi is held at v0.133.0 because oapi-codegen v2.5.1 (the platform's version) does not build against newer releases. Revisit when the platform moves to a newer oapi-codegen.
